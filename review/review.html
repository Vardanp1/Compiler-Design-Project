PROBLEM STATEMENT

Compilers tell beginners that something is wrong.
Not where to fix it, or how.

A student forgets one semicolon. The compiler points at the next line, says "expected ',' or ';' before 'printf'" and stops. The message is accurate for someone who knows the grammar. For a beginner it names the wrong line, uses parser vocabulary and never says what to type. Some real mistakes, like dividing by a variable that is zero, get no message at all.

THE PROBLEM

Where does a compiler report a mistake?

Every phase checks one thing. The report goes where the parser noticed the problem, not where the student must edit.

1Lexicalare the words valid?
2Syntaxdoes the grammar fit?
3Semanticdo the names exist?
4Codegenerate output
5Explain?where is the fix, and what is it?
THE DETECTION POINT

A parser only knows a ; is missing when it reads the next token. If that token is on line 3, line 3 is reported, although the fix belongs at the end of line 2. When the next statement is after blank lines or comments, the report moves even further away (gcc reported line 5 for a fix on line 2).

2  int b = 10        <- fix belongs here
3
4  // show the total
5  printf(...)       <- gcc reports here
THE ANALOGY

A teacher marking an essay circles the word that is misspelled and writes the right spelling in the margin. A compiler that reports the next line and says "expected ... before" is like a teacher circling the next word on the page and writing "unexpected word".

Beginners need the first kind of feedback: the place, the rule and the fix.

THE IDEA

Introducing ErrorBuddy

A small compiler whose main output, when something is wrong, is a lesson.

THE THESIS
A compiler should not just detect a mistake. It should explain it: the line, the rule and the fix.

Every error is a structured object with four fields, built by the phase that found it, and printed in one fixed format.

LINEPHASEMESSAGESUGGESTION
1

Report on the fix line

A missing ';' is reported on the line of the token before it.

2

Name the rule in plain English

"Two operators in a row: '+' followed by '*'."

3

Give one concrete fix

"Add a semicolon after '10'." Not a grammar lesson.

4

Say which phase found it

Lexical, Syntax or Semantic Analysis.

5

Stop before generating code

No partial three-address code is printed for a broken program.

THE IDEA

What makes it different

Ordinary compilers stop at detection. ErrorBuddy adds a diagnosis step before every error.

01

Four-field errors

CompileError { line, phase, message, suggestion } is the only way any phase reports a problem.

02

Diagnosis from nearby tokens

Before reporting, the parser looks at the previous and next token to name the likely cause: extra ')', missing operator, extra '='.

03

Measured typo hints

"Did you mean 'score'?" uses Levenshtein distance with a limit chosen by testing four policies on 23 typo cases.

04

Compile-time values

The symbol table tracks each variable's value, so division by a variable that is 0 is caught before the program runs.

Phases 1 to 3 in detail

From raw text to checked statements.

lexer.cpp · tokenize()

  • Counts newlines, so every token has a line
  • Skips spaces and // comments

  • Rejects @, 2nd, numbers above INT_MAX

OUTtokens ending in END_OF_FILE
2

Syntax analysis

parser.cpp · statement() …
  • Recursive descent: one function per rule
  • expression → term → factor gives precedence
  • While loops give left associativity
  • Nesting limit of 200 for (
  • Diagnoses a missing ';' before reporting

  • Use inside its own declaration

Honest limits, and what comes next

What ErrorBuddy does not do yet, from the original proposal.

KNOWN LIMITS
  • Only int, arithmetic and print. No if/else, loops or functions.
  • Stops at the first error. A program with three mistakes needs three runs.
  • No unary minus. -5 must be written as 0 - 5.
  • Values are known at compile time only because there is no input or loop.
  • TAC is the final output. There is no optimiser or machine code.
NEXT STEPS
  • if / else, while and for loops; comparison and logical operators; printf
  • Error recovery: report several errors per run
  • Functions and arrays; char and float
  • Data-flow analysis once loops and input exist
  • Constant folding on TAC, then an assembly back end
