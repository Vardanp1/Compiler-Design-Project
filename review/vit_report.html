1. Abstract

Compilers are very good at deciding whether a program is valid and much less good at telling a beginner what to do when it is not. A missing semicolon on line 2 is reported by gcc on line 3 as "expected ',' or ';' before 'printf'": the wrong line, parser vocabulary and no fix. Some mistakes, such as dividing by a variable that holds zero, are not reported at all. For a student, the time lost is spent not on the mistake but on decoding the message.

This project presents ErrorBuddy, a small compiler written in C++17 using only the standard library, for a C-like beginner language. It implements the classic phases (lexical analysis, recursive-descent syntax analysis, semantic analysis with a symbol table and three-address code generation) and treats error reporting as a phase of its own. Every error is a structured object with four fields: the line where the fix belongs, the phase that found it, a plain-English message and one concrete suggestion. Before reporting, the parser inspects the tokens around the failure to name the likely cause, and an edit-distance matcher suggests the intended name for typing mistakes.

The compiler is about 726 lines of C++, passes 10 of 10 automated example tests, and is published with a GitHub Pages website. In a case study of 24 classic beginner mistakes compared with gcc 11.4 (-Wall -Wextra), ErrorBuddy reported all 24 on the exact line where the fix belongs, while gcc reported 20 on the exact line and missed one mistake entirely.

Keywords: compiler design, error messages, novice programmers, recursive descent, symbol table, three-address code, edit distance.

2. Introduction

A compiler translates a program from a source language into a lower-level form. The classical pipeline of lexical analysis, syntax analysis, semantic analysis and intermediate code generation is designed to decide, precisely and quickly, whether a program belongs to the language. When it does not, the compiler stops and prints a diagnostic. That diagnostic is written in terms of the compiler's own grammar and reports the position where the parser noticed a problem.

For an experienced programmer this is enough. For a beginner the two weaknesses compound: the reported line is often after the line that needs editing, and the message describes what the parser expected rather than what the student should type. The fault is small and the cost is large: the student re-reads correct code on the reported line, guesses, recompiles and repeats.

An important observation motivating this project is that the information needed for a better message is already available at the moment of failure. The parser knows the previous token, the next token and the rule it was trying to complete. ErrorBuddy uses that information deliberately: diagnosis runs before the error is reported, and the report is built for the reader.

2.1 Scope of the work

  • Design of a small C-like beginner language with int variables, arithmetic, print and comments.
  • Implementation of a complete front end and three-address code generator in C++17 with no external tools (726 lines in five files).
  • An error-reporting subsystem: the four-field CompileError, token-context diagnosis, fix-line selection and typo hints.
  • An automated test suite (make test), a case study against gcc, a local web playground and a GitHub Pages website.

4. Problem Statement and Objectives

Problem statement: Compilers tell beginners that something is wrong. They do not reliably say where to fix it, or how.

Research question: How can a compiler report each beginner mistake on the line where the fix belongs, in plain words, with one concrete fix?

4.1 Objectives

  • Build a working compiler: source text to three-address code, with every core phase implemented by hand.
  • Report on the fix line: the line the student must edit, not the line where parsing stopped.
  • Explain in plain words: name the broken rule without parser vocabulary.
  • Suggest one fix: every error carries one concrete thing to type.
  • Stop broken programs: no intermediate code is printed for a program with an error.
  • Measure it: compare the reported lines with gcc on a hand-labelled set of mistakes.

5. The ErrorBuddy Language

ErrorBuddy compiles a small C-like language, kept small on purpose so that every phase could be completed and the effort could go into the error messages.

Outputprint expression;
Operators+ - * / with normal precedence; parentheses ( ); integer division
Comments// to the end of the line
Statement endevery statement ends with ;
Not includedunary minus (write 0 - 5), if/else, loops, functions, input

5.1 Grammar

program     -> statement*
statement   -> declaration | assignment | printStmt
declaration -> "int" IDENTIFIER "=" expression ";"
assignment  -> IDENTIFIER "=" expression ";"
printStmt   -> "print" expression ";"
expression  -> term (("+" | "-") term)*
term        -> factor (("*" | "/") factor)*
factor      -> NUMBER | IDENTIFIER | "(" expression ")"

6. System Architecture

The compiler is organised as five phases in three C++ source files. Phase 1 is in lexer.cpp. Phases 2, 3 and 4 run together in a single pass of parser.cpp: while a statement is recognised, its meaning is checked and its three-address code is emitted (syntax-directed translation). Phase 5, error reporting, is a shared channel used by every phase.

6.2 Shared components

  • Token: type, exact text and line number; created by the lexer and read by every later phase.
  • CompileError: line, phase, message and suggestion; the only way any phase reports a problem.
  • Symbol table: std::map from name to declaration line and current value.
  • TAC list: instructions in source order, printed by the driver only when every phase passes.

6.3 Why the diagnosis sits inside the parser

The parser is the only place that knows the previous token, the next token and the rule being completed at the moment of failure. Moving the diagnosis there lets ErrorBuddy choose the line where the fix belongs. We measured the effect with a patched build that reports the detection point instead: it placed 21 of 24 mistakes on the exact line, against 24 of 24 for the shipped fix-point rule (Section 13).

Exit codes: 0 when every phase passes, 1 for a compile error, 2 for bad usage or an unreadable file, and 3 for an internal error.

7. Phase-by-Phase Design

Phase 1: Lexical analysis

A hand-written scanner reads the source one character at a time. A newline increments the line counter, spaces and // comments are skipped, a run of digits becomes a NUMBER, a letter or underscore starts a name (the whole words int and print become keywords), and single characters become operators, '=', parentheses or ';'. The token list always ends with END_OF_FILE. It stops on an unknown symbol such as '@', a number larger than INT_MAX, or a name that starts with a digit such as '2nd'. Inspect with --tokens. Source: lexer.cpp.

Phase 2: Syntax analysis

A recursive-descent parser with one C++ function per grammar rule: statement(), declaration(), assignment(), printStatement(), expression(), term() and factor(). Precedence comes from the grammar: term() handles '*' and '/' one level below expression(), and the while loops in both make operators left-associative, so 10 - 4 - 3 is (10 - 4) - 3. factor() recurses on '(' up to a depth of 200. Stops on a missing ';' or ')', two operators in a row, a missing value, or a statement that starts with the wrong token. Source: parser.cpp.

Phase 3: Semantic analysis

The symbol table maps each name to its declaration line and current value. Checks run inside the parser the moment a name or operator is seen: undeclared variables (with a 'Did you mean' hint), duplicate declarations, a variable used in its own declaration, a keyword used as a name, division by zero and integer overflow. Because the language has no input and no loops, every value is known at compile time, so a division by a variable that holds 0 is caught before the program runs. Source: parser.cpp.

Phase 4: Intermediate code generation

binary() computes the value of each operation, checks it, takes a fresh temporary from newTemp() and emits tN = left op right. Temporaries skip any name the user wrote, parentheses produce no instructions, and the code is emitted in source order and printed only if the whole program compiles. Source: parser.cpp.

Phase 5: Error reporting

Any phase throws a CompileError at the first problem. main.cpp catches it, prints the four fields in a fixed format and exits with code 1 (Section 8). Source: lexer.h, parser.cpp, main.cpp.

8. Error Reporting Subsystem

All errors travel through one structure, defined in lexer.h so that every phase can throw it:

struct CompileError {
    int line;
    std::string phase;       // which compiler phase found the problem
    std::string message;     // what is wrong, in plain English
    std::string suggestion;  // one concrete way to fix it
};

Errors stop compilation: the program is not partly compiled, and no intermediate code is printed. This keeps one message on screen, for one mistake, at the right line.

9. Diagnosis and Typo Hints

9.1 Diagnosis from surrounding tokens

expectSemicolon() runs at the end of every statement. If the next token is not ';', it checks the token in order:

Next tokenDiagnosisReported on
')'Found an extra ')' that has no matching '('.that token's line
'='Unexpected '='. A statement can contain only one '='.that token's line
name, number or '(' on the same lineMissing operator between the two values.that token's line
anything elseExpected ';' at the end of the statement.the previous token's line (fix point)

factorError() handles a missing value: two operators in a row, a negative literal, empty parentheses, a keyword inside an expression, or a program that ends in the middle of an expression. unknownStatementError() handles a statement that starts wrongly: a misspelled or capitalised keyword, a name on its own, an extra ';' or an '=' with no name before it.

9.2 Typo hints

  1. Compute the Levenshtein distance between the unknown word and each candidate, in a single rolling row of the dynamic-programming table.
  2. Accept a candidate if the distance is at most 1 for targets of up to 3 letters and at most 2 for longer targets, and the word is not the candidate itself.
  3. Skip variable names shorter than 3 letters, which produce misleading hints.
  4. Offer the first accepted name: "Did you mean 'score'?".

The limits were chosen by testing four policies on 23 typo cases (run_study.py --hints):

PolicyRuleRightWrongMissedSilent-ok
k11 edit, all names10833
shipped1 edit if <=3 letters else 2, skip names <312615
k22 edits, all names13902
k33 edits, all names131001

The shipped policy gives the fewest wrong suggestions (6) while still getting 12 right.

14. Limitations and Future Work

14.1 Known limits

  • The language has only int, arithmetic and print; there is no if/else, loop or function.
  • Compilation stops at the first error, so a program with three mistakes needs three runs.
  • There is no unary minus; -5 must be written as 0 - 5.
  • Values are known at compile time only because there is no input and no loop.
  • Three-address code is the final output; there is no optimiser or machine code.
  • The website playground shows recorded output for the examples; compiling new code needs the local playground or the command line.

14.2 Future work

  • if / else, while and for loops; comparison and logical operators; printf.
  • Error recovery to report several errors per run.
  • Functions and arrays; char and float.
  • Data-flow analysis once loops and input exist.
  • Constant folding on TAC and an assembly back end.
  • A WebAssembly build so the website can compile any program in the browser.

15. Conclusion

ErrorBuddy shows that a small, hand-written compiler can implement every classic phase and still put the learner first. Treating each error as a structured object with a line, a phase, a message and a suggestion, and diagnosing the cause from the surrounding tokens before reporting, gives messages that point to the line where the fix belongs and say what to type. Measured on 24 classic beginner mistakes, it reported every one on the exact fix line, against 20 for gcc 11.4. Other compilers ask whether a program is valid; ErrorBuddy also answers where the mistake is and how to fix it.
